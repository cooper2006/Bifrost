架构改进设计文档
1. 引入下载状态机 (DownloadStateMachine)
现状问题： Downloader.performDownload 用 model.statusText.value = MR.strings.downloading() 等字符串来标识阶段，UI 通过 statusText 和 progress 的副本来驱动渲染。没有类型安全的状态枚举，导致：
无法精确判断当前阶段（比如 "downloading" 和 "decrypting" 都用 statusText，如果国际化翻译变化，依赖字符串的代码会失效）
新增阶段（如 V4 key 提取）需要修改多处 statusText 赋值点
无法在状态转换时执行副作用（如进入 DOWNLOADING 时自动选择目录）
设计方案：
在 common/src/commonMain/kotlin/tk/zwander/common/data/ 下新建 DownloadStateMachine.kt：
// 状态定义
sealed interface DownloadPhase {
    data object Idle : DownloadPhase
    data object FetchingInfo : DownloadPhase        // BinaryInform
    data object BinaryInit : DownloadPhase          // BinaryInit 认证
    data class Downloading(val progress: Progress) : DownloadPhase
    data class VerifyingCrc(val progress: Progress) : DownloadPhase
    data class VerifyingMd5(val progress: Progress) : DownloadPhase
    data class Copying(val progress: Progress) : DownloadPhase
    data class Decrypting(val progress: Progress) : DownloadPhase
    data class Done(val message: String) : DownloadPhase
    data class Error(val message: String, val exception: Throwable? = null) : DownloadPhase
}

data class Progress(val current: Long, val max: Long, val bytesPerSecond: Long = 0L)

// 状态机：管理合法转换
class DownloadStateMachine {
    private val _state = MutableStateFlow<DownloadPhase>(DownloadPhase.Idle)
    val state: StateFlow<DownloadPhase> = _state.asStateFlow()

    fun transition(newState: DownloadPhase) {
        // 校验合法转换（可选，可逐步加严）
        _state.value = newState
    }

    fun reset() { _state.value = DownloadPhase.Idle }
}
集成方式：
DownloadModel 持有 DownloadStateMachine 实例，替换当前的 progress、speed、statusText 三个独立字段
Downloader.performDownload 在每个阶段开始时调用 model.stateMachine.transition(...)
UI 层（DownloadView）通过 collectAsState 监听 stateMachine.state，用 when 分支渲染不同 UI
新增 Progress 状态携带 bytesPerSecond，消除独立的 speed 字段
迁移计划：
新建 DownloadStateMachine.kt 和 DownloadPhase 定义
DownloadModel 中增加 stateMachine 属性，保留旧的 progress/speed/statusText 作为适配桥接（derivedStateOf 从 stateMachine 映射过来）
逐步替换 Downloader 和 DecryptView 中的状态赋值
最后删除旧的三个独立字段
2. 拆分 Downloader.performDownload 长方法
现状问题： performDownload 约 220 行，包含 6 个阶段（BinaryInit 重试循环、下载、CRC32、MD5、文件复制、解密），硬编码在单个函数内。
设计方案：
将 Downloader 从 object 改为可实例化的类，接收 DownloadModel 作为构造参数。将 performDownload 拆分为多个阶段方法，每个方法返回 Result 或 DownloadPhase：
class Downloader(
    private val model: DownloadModel,
    private val fileManager: FileManager,
    private val cryptUtils: CryptUtils,
) {
    // 对外入口
    suspend fun onDownload(confirmCallback: DownloadErrorCallback)

    // 内部阶段，每个阶段一个方法
    private suspend fun retrieveFileInfo(): Result<BinaryFileInfo>
    private suspend fun performBinaryInit(fileName: String): Result<Unit>  // 含重试
    private suspend fun downloadFile(info: BinaryFileInfo, encFile: IPlatformFile): Result<String?>
    private suspend fun verifyCrc32(encFile: IPlatformFile, expectedCrc: Long): Result<Unit>
    private suspend fun verifyMd5(encFile: IPlatformFile, expectedMd5: String): Result<Unit>
    private suspend fun copyToDest(encFile: IPlatformFile, destFile: IPlatformFile): Result<Unit>
    private suspend fun decryptFile(encFile: IPlatformFile, decFile: IPlatformFile, info: BinaryFileInfo): Result<Unit>
}
阶段上下文 Data Class：
data class DownloadContext(
    val info: BinaryFileInfo,
    val fullFileName: String,
    val downloadDirectory: IPlatformFile,
    val tempDirectory: IPlatformFile?,
    val encFile: IPlatformFile,
    val extractedEncFile: IPlatformFile,
    val decFile: IPlatformFile?,
    val decKeyFile: IPlatformFile?,

集成方式：
Downloader.onDownload 调用 retrieveFileInfo()，成功后构造 DownloadContext，然后依次调用各阶段方法
每个阶段方法接收 DownloadContext 并返回 Result<Unit>，失败时尽早返回
重试逻辑（BinaryInit 的 10 次循环）封装在 performBinaryInit 内部，不泄露到主流程
3. 解决 FusClient 并发安全问题
现状问题： FusClient 是 object，nonce/auth/sessionId 用 @Volatile 但 check-then-act 不是原子的。多协程同时调用 getNonce() 可能触发多次 generateNonce()；makeReq 和 downloadFile 可能同时读写 nonce。
设计方案：
方案 A（推荐，改动最小）：使用 Mutex 保护关键读写
object FusClient : IFusClient<FusClient.Request> {
    private val authMutex = Mutex()
    
    private var nonce: String = ""
    private var auth: String = ""
    private var sessionId: String = ""

    override suspend fun getNonce(): String = authMutex.withLock {
        if (nonce.isBlank()) {
            generateNonceInternal()
        }
        nonce
    }

    // 内部方法，假设调用方已持有锁
    private suspend fun generateNonceInternal() { ... }
    
    // makeReq 中更新 nonce 的地方也需在锁内
    override suspend fun makeReq(...): String = authMutex.withLock {
        // ... 原有逻辑
    }
}
方案 B（更彻底）：将会话状态封装为 FusSession data class，每次需要新会话时创建新实例。
选方案 A，因为：
改动范围小，不破坏现有 API 签名
锁的粒度可控，downloadFile 的大文件下载不持有锁
容易迁移，后续可平滑过渡到方案 B
需要修改的文件：
FusClient.kt：为 nonce/auth/sessionId 的读写加 Mutex，makeReq 和 getNonce/generateNonce 在锁内执行
FusClientLegacy.kt：同样处理

5. 统一重试策略
现状问题： 三个重试循环各自独立：
FusClient.makeReqWithRetry：while 循环，最多 3 次，无 backoff
FusClient.downloadFile：while 循环，最多 3 次 auth 重试，无 backoff
Downloader.performDownload：while 循环，最多 10 次，无 backoff
设计方案：
在 common/src/commonMain/kotlin/tk/zwander/common/util/ 下新建 Retry.kt：
/**
 * 带指数退避的重试工具。
 * @param maxRetries 最大重试次数
 * @param initialDelay 首次重试延迟（毫秒）
 * @param maxDelay 最大延迟上限（毫秒）
 * @param retryable 判断异常是否可重试
 * @param block 实际执行的操作
 */
suspend fun <T> retryWithBackoff(
    maxRetries: Int = 3,
    initialDelay: Long = 500L,
    maxDelay: Long = 30_000L,
    retryable: (Throwable) -> Boolean,
    block: suspend () -> T,
): T
使用方式：
// FusClient 中的 401 重试
val body = retryWithBackoff(maxRetries = 3, retryable = { it is AuthExpiredException }) {
    makeReqInternal(request, data, signature, includeNonce)
}

// Downloader 中的 BinaryInit 重试
retryWithBackoff(maxRetries = 10, initialDelay = 1000L, retryable = { 
    it is AuthExpiredException || it is SocketTimeoutException 
}) {
    performBinaryInitInternal(...)
}
修改范围：
新建 Retry.kt 工具函数
FusClient.kt 的 makeReqWithRetry 改为使用 retryWithBackoff
FusClient.kt 的 downloadFile 中的 auth 重试改为使用 retryWithBackoff
Downloader.kt 的 performDownload 中的 BinaryInit 重试改为使用 retryWithBackoff
6. BaseModel 职责拆分
现状问题： BaseModel 同时管理状态字段（model/region/fw/imeiSerial/statusText/speed/progress）和协程生命周期（launchJob/endJob/_jobs）。endJob 取消所有协程，过于粗暴。
设计方案：
将协程管理拆分为独立类 JobManager：
// 新文件: common/src/commonMain/kotlin/tk/zwander/commonCompose/model/JobManager.kt
class JobManager {
    private val scope = CoroutineScope(Dispatchers.IO + SupervisorJob())
    private val _hasRunningJobs = MutableStateFlow(false)
    val hasRunningJobs: StateFlow<Boolean> = _hasRunningJobs.asStateFlow()

    fun launch(block: suspend CoroutineScope.() -> Unit): Job {
        val job = scope.launch(block = block)
        job.invokeOnCompletion {
            _hasRunningJobs.value = scope.coroutineContext[Job]?.children?.any { it.isActive } == true
        }
        _hasRunningJobs.value = true
        return job
    }

    fun cancelAll() {
        scope.coroutineContext[Job]?.children?.forEach { it.cancel() }
        _hasRunningJobs.value = false
    }

    fun cancel(job: Job) {
        job.cancel()
    }
}
BaseModel 精简后只保留状态管理：
abstract class BaseModel(modelKey: String) {
    // 只保留状态字段
    val model = ...
    val region = ...
    val fw = ...
    val imeiSerial = ...
    val statusText = MutableStateFlow("")
    val speed = MutableStateFlow(0L)
    val progress = MutableStateFlow(0L to 0L)

    // 协程管理委托给 JobManager
    val jobManager = JobManager()
    val hasRunningJobs: Flow<Boolean> = jobManager.hasRunningJobs

    fun launchJob(block: suspend CoroutineScope.() -> Unit): Job = jobManager.launch(block)

    fun endJob(text: String) {
        jobManager.cancelAll()
        progress.value = 0L to 0L
        speed.value = 0L
        statusText.value = text
        onEnd(text)
    }

    protected open fun onEnd(text: String) {}
}
优势：
JobManager 可复用（DecryptModel、HistoryModel 也需要协程管理）
endJob 不再遍历和取消子协程，而是通过 SupervisorJob 让子协程独立失败
cancelAll 只取消根协程，子协程自然失效
